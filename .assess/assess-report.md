<summary>🧭 How to read this report (framing & method)</summary>

**What this is ultimately measuring.** When you hand work to an AI here, does it behave like a brand-new hire or like an engineer who has been in the org eighteen months? The difference isn't capability - it's *externalized context*: knowing where things live, which contracts other code relies on, where the minefields are. An AI contributor is structurally always the new hire - it starts every session with an empty head, seeing one narrow slice through its context window - so this report scores how much of the tenured engineer's implicit map the codebase has made explicit and navigable. **Legibility you can trust, not omniscience you can't.**

This is an improvement roadmap, not a verdict. It pairs three views: the complexity heatmap (where the codebase is today), the doc graph (whether an agent can navigate it), and the headline with the per-practice scorecard (what keeps it from getting worse). A **Next up** or **Partly in place** locates where someone working here is partly blind; it is not a mark against the code.

**The legacy-transition lens.** "Legacy code is code without tests" (Michael Feathers): pin current behaviour with characterization tests, find a seam, then refactor. Prefer the Strangler Fig over a rewrite, treat the hotspot and change-coupling findings (Adam Tornhill) as the worklist, and decide per component with the 7 Rs.

**How it's measured.** Static analysis, git history and graph metrics over the docs and code; the model only writes the prose around those numbers.
