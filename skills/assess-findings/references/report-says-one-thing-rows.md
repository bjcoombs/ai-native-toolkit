# Says one thing, does another: the row rules

How to fill each row of the "Says one thing, does another" table in the report template of the assess-findings skill, and the `lying_map` paths line under it.

- **Agent instructions - stale hub doc:** take `stale_hubs[0]` only when `stale_hubs` is a list (an object with `available: false` means the ranking failed: no row) and its `ratio > 2.0` **and** `confidence != "low"` (a `repo-baseline` subject is `confidence: low` - its "subject churn" is the whole repo's churn, too coarse to say the doc and the code disagree). Fill from `path`, `last_commit_days`, `code_churn_in_window`, and present the doc as a candidate to read again, not a verdict: churn says the subject moved, not that the doc is wrong.
- **Agent instructions - false instruction claim:** when `instruction_claims.failed > 0`, take the first entry of `instruction_claims.failures` that the scorer confirmed and cited in the agent-instructions evidence; when it confirmed none, no row. Fill from `file`, `line`, `path`, `kind` and `reason` (`enforcement`: no CI configuration or task runner references the script; `pin`: the pinned file lacks `version` or does not exist; `count`: the sentence claims `claimed` files for the pattern and `actual` match - print both numbers). Name the count when more than one was confirmed ("and <n - 1> more").
- **Agent instructions - conflicting doc claims:** when `doc_claims.contradictions_total > 0`, take the first entry of `doc_claims.contradictions` that the scorer confirmed and cited in the agent-instructions evidence; when it confirmed none, no row. Fill from `kind`, `path` and the two `conflict_pair` sites (two different files whose values disagree) as `<file>:<line>` with each `value` (`pin`: two versions pinned in `path`; `count`: two counts for the pattern `path`). Name the count when more than one was confirmed ("and <n - 1> more").
- **Agent instructions - ignored Claude Code config:** when `claude_config.available` is true and `claude_config.findings` holds an entry that is neither `legacy_command` nor a `command_unsupported_key` with `key: name`, take the first such entry; fill from `file`, `line`, `key`, `value` and `kind`, and end the Why cell with its `fix`. Name the count of the others when there are more ("and <n - 1> more"). Legacy command files and `name` in a command file alone get no row (both still load; a repo may keep `name` for another loader); mention them in the agent-instructions evidence instead, with the count from `claude_config.counts_by_kind.legacy_command`. `available: false` means no Claude Code configuration was found: no row, and never report it as clean. The row is an agent-instructions detail: it does not change the findings number on the badge.
- **Runtime legibility - dead-but-present:** take `dead_code.candidates[0]`; fill from `path`, `symbol`, `kind`. Keep the `dead_code.caveat` in mind - static reachability proves "nothing in this repo calls it," never "no external consumer calls it" - so frame it as a candidate, not a verdict.
- **CI and the agent's local check - config snapshot drift:** take `config_drift.entries[0]` (ranked worst first) only when `config_drift.available` is true; fill from `file`, `key`, `tracked`, `live` (a changed list carries `count`, `removed`/`added` and a short `sample` of names, not the list itself). `available: false` means the comparison did not run (`reason` says why; `no_access` when the token cannot read the setting) - no evidence either way, so no row.
- **Coverage gates and truth pressure - green-but-hollow:** take `test_pressure.survivor_clusters[0]` only when `test_pressure.survivor_density.overall > 0.3`; fill the file from the cluster's `file`. State the mutation score as the overall score, `1 - survivor_density.overall`, and label it overall: it covers every mutated file, not the one named. Pair it with the file's line coverage when you have it. This is the hollow-gate pattern the coverage practice scores Partly in place for.
- **Review on merged pull requests - hollow required review:** add the row when `review_reality.hollow_required_review` is true (review is required and under 20% of sampled merged pull requests carry any review from someone other than the author: nobody looked) or `review_reality.required_approval_bypassed` is true (review is required and under 20% carry an approval from someone other than the author: a review bot may comment, but the required approval does not happen). Name which flag fired. Fill from `merged_count`, `reviewed_share`, `approved_share` and `self_merged_share` as percentages; the block holds counts and shares only, so name no pull request or account. The rules are read as they stand now; when `oldest_merged_days_ago` reaches back before the rule could have existed, say so. `available: false` or null flags (unreadable rules, or under 5 merged pull requests) - no row. On a GitLab remote (merged merge requests via `glab`) `reviewed_share` and `bot_review_share` come from the merge requests' approvals and notes; a null there means a merge request's notes were too many to decide within the up to 3 pages (300 notes) read - write the row from `required_approval_bypassed` and `approved_share`, and leave the reviewed percentage out rather than reporting it as unavailable.
- **The `lying_map` finding:** when its `paths` is non-empty, list them under the table (or alone, when no row qualifies) as `Stale doc over complex code:` followed by every path, so each one sits above the first fold. The finding also stays, verbatim, in the cross-practice findings fold.
