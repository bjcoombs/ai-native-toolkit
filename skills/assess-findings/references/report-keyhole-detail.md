# The keyhole detail entries

The entries of the report template's "🔎 Cross-practice findings" fold in the assess-findings skill that come before the pasted `findings_markdown`. Text in angle brackets and the bold paragraphs are instructions for how to fill them.

### Instruction placement

<Agent instructions evidence, from `instruction_placement`. One line per entry of `files` that has a `relocatable` section or is `flagged`: `<path>` - `<always_on_lines>` of `<total_lines>` lines always-on (`<always_on_share>` as a percent), "flagged" when `flagged` is true. Under it, one bullet per `relocatable` entry: `<path>:<start_line>-<end_line>` *<heading>* (`<lines>` lines; `<signals>`) → `<home.kind>` `<home.target>`; for `existing_skill`, "replace with a pointer to `<home.target>`". Add "and <relocatable_total - len(relocatable)> more" when the list was cut short. Then a separate **Loaded in full (informational)** line per `loaded_in_full` entry, in its order (most tokens first): `<path>` (`<kind>`, `<total_lines>` lines, about `<est_tokens>` tokens, `<always_on_share>` always-on), with its relocatable sections as bullets in the same form (home `reference_doc`, or `existing_skill` when the text is already in another skill; a `null` `reference_doc` target reads "a reference document the agent reads on need"). When `files` holds no flagged file and no relocatable section, one line: "no instruction-file section clearly belongs outside the always-loaded layer". Moving the largest sections of a flagged instruction file is a Top 3 candidate (see the scorer's agent-instructions rule); `loaded_in_full` never ranks. Not a "Says one thing, does another" row, not counted on the badge; the instruction file's grade carries the same split through its `bloat_penalty`, and `loaded_in_full` has no grade effect. `available: false`: "instruction placement not checked" with the `reason`.

**Skill disclosure**, from `skill_disclosure` (#1045). It feeds the skill-disclosure condition. One line per entry of `files` whose `breaks` is not empty: `<path>` (`<kind>`), then each rule it breaks in words: `body_lines` "body over 500 lines (`<body_lines>`)", `tokens` "about `<est_tokens>` tokens, over 5000", `name_missing` "no `name`", `description_missing` "no `description`", `description_long` "description of `<description_chars>` characters, over 1024", `reference_missing` "links `<target>`, which does not exist" (each `references` entry with `resolved` false), `reference_deep` "`<target>` is reached only through another reference" (each `references` entry with `depth` 2). For `body_lines` or `tokens`, add the relocation `instruction_placement` suggests: the same path's `loaded_in_full` relocatable sections, in the form above. When `files_considered` is 0, one line only: "no skill or agent file to check" (not measured, never a pass). Otherwise, when no file breaks a rule, one line: "every skill and agent file follows the disclosure guidance". Unit readings: a skill unit reads its own folder's file; other units inherit the repository's reading.

**Secrets guard**, from `secrets_guard` (#1173). It feeds the secrets-guard practice. One line: the guards found, each with its own grade from `sources` (a pre-commit hook `pre_commit.tools`, "configured, can be skipped with --no-verify"; a CI scan `ci.tools` in `ci.files`, "secrets scan detected in CI"; `platform`, "GitHub secret scanning or push protection is on"), or "no pre-commit or CI secrets guard detected" (GitHub's own secret scanning is a repository setting, read only on the platform pass: when it was not read, never say the repository has no guard at all; when it was read and both settings are off, with no hook or CI scan, say there is no secrets guard). Level 1 (any guard) is listed, not counted; level 2 needs a CI scan (a failing check can gate the merge) or GitHub push protection (it rejects the push) (`enforcement.source`); secret scanning alone raises an alert that gates nothing. When `enforcement` is `available: false` (`secret_scanning_not_read`), say level 2 was not measured: GitHub's own push protection was not read (it needs `gh` signed in as a repository admin, organization owner or security manager); when it is `ci_includes_unresolved`, say a GitLab include that could hold the scan was not read. When it is `gitlab_rules_unevaluated`, name the scans in `ci.rules_unevaluated` and say they run under GitLab rules this reader does not evaluate. Never call it missing. When no CI scan runs, name the fix: add a secrets scan step to CI (`gitleaks/gitleaks-action` or `trufflesecurity/trufflehog`); when the platform block was read with push protection off, also name turning on GitHub push protection. GitHub's per-user push protection on public repositories is not a repository setting and each pusher can turn it off, so it does not change this reading. When push protection meets level 2 and `github_secret_scanning.delegated_bypass` is false, add that a pusher can bypass a block by stating a reason, which GitHub records.

**Skill script tests**, from `skill_script_tests` (#1045). It feeds the skill-script-tests condition, which checks that tests exist beside a skill's scripts, not how much they cover: no suite runs. One line per entry of `skills` whose `untested` is true: `<path>` (`<scripts>` scripts, no tests in the skill's folder). When its `tested_elsewhere` is not empty, add "tested from outside the skill folder (`<tested_elsewhere>`); those tests won't ship with the skill", and give the fix "move or copy the tests into the skill's folder"; otherwise the fix is "add tests beside the scripts in the skill's folder". When `skills_with_scripts` is 0, one line only: "no skill holds a script to test" (not measured, never a pass). Otherwise, when no skill is untested, one line: "every skill's scripts have tests beside them". A skill unit reads its own folder; other units inherit the repository's reading.

**Personal data in skill text**, from `skill_personal_data` (#1045). It feeds the skill-personal-data condition. One line per entry of `files`: `<path>` holds <the `kinds` in words: an email address, a phone number, a personal home path, an IP address, an SSH login, a cloud key, a private key, a credential>. Name the file and the kind only: never quote, paraphrase or locate the data itself, and never open the file to show it. The fix: remove it or replace it with a placeholder (`user@example.com`, `/home/user/`), and rotate any key that was committed. When `credential_candidates` is above 0, add one line: "<n> file(s) hold a credential-shaped assignment with what looks like an example value, listed for information only", never as a leak. When `files_considered` is 0, one line only: "no skill or agent file to scan" (not measured, never a pass). When `available` is false (`skill_files_unread`), say the scan was partial: `files_unread` files could not be read, so a clean reading is not claimed. Otherwise, when `files` is empty, one line: "no skill or agent file holds an email, phone number, home path, IP address, SSH login, key or credential"; say that these are the kinds checked, so it is not read as "no personal data of any kind" (names are not checked). A skill unit reads its own folder; other units inherit the repository's reading.

**Contributor files**, from `contributor_files` (#1045). It feeds the contributor-files condition. One line: the contributing guide (`guide.path`, or "no contributing guide"), the security policy (`policy.path` with "a SECURITY file", "a link to GitHub private vulnerability reporting" or, for `policy.source` `org`, "policy: org .github, read from the GitHub API" from `policy.kind`, or "no security policy"), and, as evidence only, whether issue and pull or merge request templates are committed. When `policy` is `available: false` (`org_policy_not_read`), say the policy was not measured: the repository holds none and the owner's shared `.github` repository was not read, and a run with `gh` signed in (or `fleet --platform`) reads it. Never call that policy missing. When `ready` is false, name what to add: a `CONTRIBUTING.md` that says how to build, test and shape a change, a `SECURITY.md` that says how to report a vulnerability privately, or both. `available: false` with a `knowledge_base` reason: "not measured for a knowledge base".>

**Skill library**, from `skill_library` (#848). It feeds the skill-library condition. One line: the count of skills counted (`skills_counted`) and the locations they sit in (each distinct `skills[].location`). When `shared_by_symlink` is not empty, add one line per entry: `<path>` links to `<target>`, so several harnesses read one tree. Name a committed `lock_files` or `hashed_manifests` entry as evidence that the library is pinned. When `invalid_frontmatter` is above 0, one line naming each `invalid_files` path: its frontmatter is missing, does not parse or has no `name` or `description`, so it does not count. When `present` is false, say no committed skill library was found, add the set-aside counts in words (`set_aside_vendored` under node_modules or vendored folders, `set_aside_fixture` in fixture folders, `set_aside_location` outside a known skill location, `symlinks_outside` symlinks that leave the repository) when any is above 0, and the fix: commit a `skills/<name>/SKILL.md` or `.claude/skills/<name>/SKILL.md` with a `name` and a `description`. `available: false` with `not_a_git_repository`: say the reading is not measured, never that no library exists.

**Model-backed CI jobs**, from `ci_model_jobs` (#1242). It feeds the model-ci-gated condition. One line per entry of `jobs` whose `state` is `ungated`: `<path>:<line>` job `<job>` runs a model (`<signs>` in words: an eval harness, an agent action, the Claude Code CLI, a model-provider secret, eval tests) on every `<triggers>` with no gate; add "superseded runs are cancelled, which lowers the cost but still runs every update" when `cancel_superseded` is true. Then the fix, short: run the job only when prompts, skills or instruction files change (a `paths:` filter or GitLab `rules:changes:`), or nightly, or on a label; cancel superseded runs; sample the eval cases or cache results by content hash; use the cheapest model that still tells a good result from a bad one; move rule-checkable assertions into ordinary tests. For each `unknown` entry, one line naming `<path>:<line>` and its `reason` in words (`secret_only`: the job only names a provider secret, perhaps to store or pass it on), and say it was not measured, never that it is ungated. When `model_jobs` is 0, one line only: "no model-calling CI job detected" (not measured, never a pass). When `ungated` is null with `ci_jobs_unread`, say a reusable workflow from another repository or a GitLab include was not read, so the reading is not measured. When `ungated` is null with `trigger_unresolved`, say the reading is not measured. Only when `ungated` is 0 and no job is `unknown`, one line: "every model-backed CI job is gated", naming each job's `gates`.

### Agent harness

<Informational, beside the Claude Code configuration evidence. From `agent_harness`: one line naming what the committed agent configuration runs on every session, from `executes_by_kind` (e.g. "2 settings hooks, 1 MCP server (`.mcp.json`: `db` runs `npx`)"), or "no committed hooks, env, apiKeyHelper or MCP servers" when `executes` is empty. Then one bullet per entry of `findings`: `<file>[:<line>]` - `<detail>` (`<kind>`), ending with its `fix`. Never print a value the block does not carry: it names a tracked `.env` by path and an `env` variable by name only, and reports hidden characters as code points. When `tracked_known` is false, add "tracked-file checks not run (not a git repository)". A `tracked_env_file` or `tracked_local_settings` finding is a Top 3 candidate (see the scorer's agent-instructions rule); the rest stay here. Not a "Says one thing, does another" row and not counted on the badge.>

### Agent consistency

<From `agent_consistency`: does every agent system get the same map? With `applicable` false, one line: "one agent system (`<systems>`): nothing to compare". Otherwise open with "<systems_total> agent systems; canonical source `<canonical>`". When `consistent` is true, one line saying every system reads the same instructions. Otherwise **Differences**: one bullet per `divergences` entry, a command as `` `<value>` `` named in `<named_in>`, missing from `<missing_from>`, a threshold as `<value>` stated as the `stated` numbers per system. Then **Next steps**: one bullet per `next_steps` entry, `<path>` (`<system>`): its `pointer` verbatim in a code span as the line to add to that file (for Aider, an entry under `read:` in `.aider.conf.yml`; keep the file's other settings), and `symlink` verbatim as the alternative when not null. Never rewrite a pointer line and never write one for a system the block does not list. Supportive voice: a shared source is what keeps every tool's agent on the same checks, never a failing. Not a "Says one thing, does another" row.>

### Agent environment

<CI and the agent's local check evidence, from `agent_environment`. One line each: **Setup** - the `setup.sources` paths, or "none committed"; **Check** - `check.named[0]` as `<file>:<line>` `<command>`; when `named` is empty and `check.unresolved` is not, its first entry as `<file>:<line>` `<command>` "does not resolve" with its `reason` (fix that command, do not add a second); when both are empty, "no instruction file names a check command" and the `check.entry_points` commands it could name; **Pinning** - the manifests with `locked: false`, or "every manifest locked" (`all_locked: null`: no manifest); **CI duration** - `slowest_median_seconds` as minutes for `branch` over `runs_sampled` runs against the 10-minute guidance, or `ci_duration.reason` when unavailable. Then the cap: when `layer5_cap.applies`, "CI and the agent's local check: held at Partly in place (<reason>)". One bullet per `findings` entry: `<file>[:<line>]` - `<detail>` (`<kind>`), ending with its `fix`. A CI practice held at Partly in place makes the missing piece a Top 3 candidate: name the instruction-file line to add or the setup file to commit. Not a "Says one thing, does another" row and not counted on the badge.>

### Guardrails stated

<From `guardrails`: do the instruction files tell an agent what the gates enforce, so the next session does not trip over the same gate? Open with one line: "<stated> of <enforced> configured gates are stated in the instruction files". Then **In place**: one bullet per gate with `stated: true`, `<kind>` (`<tool>` `<rule>`, threshold `<threshold>` when not null) at `<file>[:<line>]`, stated in `<stated_in>`. Then **Next steps**: one bullet per gate with `stated: false`, the gate as above, followed by its `snippet` verbatim in a code span as the line to add to `CLAUDE.md` or `AGENTS.md`. Never rewrite a snippet and never write one for a gate the block does not list. With `enforced` 0, one line: "no configured gate found to state" and the `not_read` forms. `available: false`: "guardrails not checked" with the `reason`. Supportive voice: a stated gate is something the repository already does well, an unstated one is a ready line to add, never a failing. Adding the snippets is a Top 3 candidate when two or more gates are unstated. Not a "Says one thing, does another" row.>
