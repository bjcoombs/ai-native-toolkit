# CI and merge gates

The CI reference for `ai-native-toolkit`, moved out of the root `CLAUDE.md` so it is read when needed rather than on every task. `CLAUDE.md` keeps the commands and the list of required checks; this page holds the why. Back to the [Map of Content](../index.md).

## Workflows

- `.github/workflows/pr-lint.yml` validates PR titles against conventional-commit format and auto-applies the matching label (`feat` / `fix` / `docs` / `chore` / `refactor`). Other conventional types (`ci`, `build`, `test`, `perf`, `style`, `revert`) pass validation but get no label.
- `.github/workflows/tests.yml` runs three pytest jobs (`skills/assess pytest`, `scripts/ pytest`, `plugin contract pytest`) plus a `ruff + mypy gates` lint job (Layer 3 complexity ratchet + Layer 2 type gate) on every PR and push to `main`. A red test is a real regression: the deterministic core is reproducible, so flakes should not happen. The three pytest jobs run on every core with pytest-xdist (`-n auto --dist loadfile`, [#930](https://github.com/bjcoombs/ai-native-toolkit/issues/930)): each test file stays on one worker, so state shared across a file's tests ([#831](https://github.com/bjcoombs/ai-native-toolkit/issues/831)) cannot interleave, and pytest-cov combines the workers' data before the coverage floor is checked. pytest-xdist is in the locked dev group of `skills/assess` and `scripts/`; `tests/` has no lockfile, so its job adds it with `--with` at the same range. `make check` uses the same flags; `make check XDIST="-p no:xdist"` runs serially for debugging. Tests marked `cpu_budget` assert an absolute CPU-time budget, so they skip inside an xdist worker and a serial step after each parallel `skills/assess` run executes them (`-p no:xdist -m cpu_budget --no-cov`, here and in `windows.yml`). The runner's 4 vCPUs are 2 cores with 2 hardware threads each, and a busy worker on the sibling thread roughly doubles a test's CPU seconds: the Dart scanner's `unclosed-functions` case went from 0.57 s per scan serially to 1.01 s under `-n auto`, past its 1 s budget. [#929](https://github.com/bjcoombs/ai-native-toolkit/issues/929) replaces that absolute budget with a scaling ratio that contention does not move.
- `.github/workflows/windows.yml` runs the Windows suites as parallel matrix legs ([#938](https://github.com/bjcoombs/ai-native-toolkit/issues/938)), `windows / assess 1/5` to `windows / assess 5/5`, `windows / scripts-contract`, `windows / ghsync 1/2`, `windows / ghsync 2/2` and `windows / smoke`, with `fail-fast` off so one red leg does not cancel the rest. Branch protection requires only the aggregator job `windows suites + smoke runs` ([#754](https://github.com/bjcoombs/ai-native-toolkit/issues/754)). It runs on every workflow run (`if: always()`, `needs: suites`) and passes only when `needs.suites.result` is `success`, so a failed, cancelled or skipped leg or shard fails it. A `concurrency` group per pull request (`windows-<PR number>`, or the commit SHA on a push) cancels a PR's older run when a new commit arrives; the cancelled aggregator reports only on the superseded commit, and pushes to `main` never cancel. The `assess` legs each run one shard of `skills/assess pytest`, and shard 1 also runs the fleet golden run and the serial `cpu_budget` step; `scripts-contract` runs `scripts/ pytest` and `plugin contract pytest`; the two `ghsync` legs each run one shard of the ghsync and ghreport suites; the shards come from `tests/pytest_shard.py` (`-p pytest_shard --shard K/N`), which assigns whole test files, heaviest first, to the lightest shard, so `--dist loadfile` still holds each file on one worker. `skills/assess` files are weighted by the Windows seconds per file in `skills/assess/tests/shard-weights.json` (a file missing from it counts as the median), the ghsync and ghreport files by size. Each sharded leg records the seconds each file took (`--shard-record`) and uploads them as the `shard-seconds-<suite>-<K>` artifact; to rebalance, merge the five assess artifacts of a green run with `jq -S -s add` into that file (one run's per-file times are noisy, so the committed file averages three runs, each normalised to its total). The GitLab contracts of ghsync and ghreport are split over several files (fixture and stubs in `tests/ghsync_gitlab_env.py` and `tests/ghreport_gitlab_env.py`), because a single file runs on a single worker: `test_ghsync_gitlab.py` alone took about 10 minutes on Windows. The plan places each collected file once by construction, so the N shards of a suite are disjoint and together hold the full collection as long as every leg collects the same files with the same arguments: `tests/test_windows_workflow.py` checks that `--shard` is the only per-leg argument and that every shard number appears once, and `tests/test_pytest_shard.py` runs the plugin on real collections and checks the union; `smoke` runs the CRLF check, the standalone ZIP build, the eval scaffolds and the smoke runs. Each leg runs on `windows-latest` with the same setup: Python 3.11 (the SVG smoke step alone runs on 3.12), ripgrep 15.2.0 (choco with three tries, then the SHA256-checked GitHub release zip) and jq, the Git for Windows baseline from [#749](https://github.com/bjcoombs/ai-native-toolkit/issues/749). The checkout has `core.autocrlf` off so fixtures keep LF endings; the step `Shell scripts are LF in a CRLF checkout` makes a fresh clone of the commit with `core.autocrlf=true`, the default a Windows user gets, and fails if any tracked `*.sh` holds a CR byte there (`.gitattributes`, `*.sh text eol=lf`, keeps them LF). The first step of the `assess` leg, `Fleet golden run against the committed Linux repos.jsonl`, runs `skills/assess/tests/test_fleet_golden.py`: a three-repository fixture estate built at test time goes through `fleet.py`, and its `repos.jsonl` must equal `skills/assess/tests/fixtures/fleet_golden/repos.jsonl`, which the Linux `skills/assess pytest` job also checks (regenerate it with `FLEET_GOLDEN_REGEN=1`, see the test's docstring). Then every suite runs in its leg, each step even when an earlier one in that leg failed, on every core with pytest-xdist (`-n auto --dist loadfile`, so each test file stays on one worker and cross-file state such as [#831](https://github.com/bjcoombs/ai-native-toolkit/issues/831) cannot interleave; from each package's locked dev group, and with `--with` for `tests/`, as in `tests.yml`) and with no coverage gate (the Linux jobs own the floors): `skills/assess pytest`, `scripts/ pytest`, `plugin contract pytest` (`tests/`) and the ghsync and ghreport suites (`tests/test_ghsync*.py`, `tests/test_ghreport*.py`) under Git Bash (`shell: bash`). Those suites take about 7 minutes in two shards, so on a pull request they run only when its diff against the base touches `skills/ghsync/`, `skills/ghreport/`, `tests/gitbash.py`, `tests/conftest.py`, `tests/pytest_shard.py`, `tests/ghsync_gitlab_env.py`, `tests/ghreport_gitlab_env.py`, `tests/test_ghsync*.py`, `tests/test_ghreport*.py` or `windows.yml`; the step `Decide whether the ghsync and ghreport suites run` logs which, and a push to `main` always runs them ([#971](https://github.com/bjcoombs/ai-native-toolkit/issues/971)). The gate is a step condition inside the `ghsync` leg, not a workflow `paths:` filter or a job-level `if:`, so the leg still reports success when the suites skip and the required aggregator always reports. The `smoke` leg builds the standalone ZIPs and runs every `evals/**/scaffold.sh`. Tests that need POSIX-only machinery skip on Windows: they carry a marker from `WINDOWS_SKIP_MARKERS` in `skills/assess/tests/conftest.py` (`needs_symlink`, `needs_posix_perms`, `needs_posix_shell`), or their fixture calls `skip_without_posix_shell()` because it puts a `#!/bin/sh` `gh`/`glab` stub on `PATH`. Two tests that run with no `glab` on `PATH`, `test_missing_glab_fails_fast` (`tests/test_ghsync_gitlab.py`) and `test_from_list_works_without_glab` (`tests/test_ghsync_gitlab_from_list.py`), skip on any OS when a real `glab` sits in the same directory as a tool the script needs (on Windows, a Git Bash tool directory goes on `PATH` whole), because that `glab` cannot then be left off `PATH`. The golden masks `last_commit_days`, which is measured against the wall clock, so the comparison holds on any date. The tests reach Windows through `tests/gitbash.py`: `bash` resolved on `PATH` (not System32), stubs and data files written with LF endings, `os.pathsep` in `PATH`, the Windows start-up variables carried into scratch environments, and read-only git objects cleared before a test deletes a bare repository. The scripts themselves pass `--binary` to jq under Git Bash when the jq on `PATH` accepts it, because a native `jq.exe` writes CRLF line endings; a POSIX jq 1.6 from MSYS2 or Cygwin rejects the flag and runs unwrapped (`tests/test_gitbash.py`). The one POSIX-only test, the interrupted capture stopped with `os.killpg`, skips on Windows.
- The `smoke` leg ends with smoke runs on fixtures. A ghsync-layout estate of two repositories (`acme/widget/widget-main`, `acme/gadget/gadget-main`) whose source and commit subjects hold non-ASCII text is built in the step. `assess_signals.py` and `assess_core.py` run on one of them, and `assess_report.py --stdout` must give UTF-8 with the headline `·` and the commit subject intact. The step `Smoke the SVG scripts on Python 3.12` then runs `complexity-treemap.py` and `doc-graph-svg.py` on the same repository through `uv run --python 3.12 <script>`, which builds each script's environment from its inline `requires-python >=3.12` and dependency header while the project environment stays on 3.11 ([#968](https://github.com/bjcoombs/ai-native-toolkit/issues/968)); `tests/fixtures/windows_smoke/check_svg.py` fails the step unless each script wrote a non-empty SVG that decodes as UTF-8 and parses with a root `<svg` element. `fleet.py` runs over the root and with `--from-list` (`--no-history`), and `tests/fixtures/windows_smoke/check_fleet_rows.py` checks both `repos.jsonl` files: LF endings, one `ok` row per repository. `tests/fixtures/windows_smoke/longpath.py` builds a repository with `core.longpaths=true`, as a ghsync clone has it, holding one Python module whose absolute path is over 300 characters, past Windows' 260-character limit; `assess_signals.py` and `assess_core.py` (with `vulture` added through `uv run --with`, since it is not a locked dependency) run over it, and the checker fails the step when lizard (complexity), grimp (structure), vulture (liveness) or rg (markers) reports a reading that leaves that module out. Every scanner is installed, so the step passes `--require-all` and a scanner whose block is unavailable (read as not measured, with the block's reason) fails it too ([#1405](https://github.com/bjcoombs/ai-native-toolkit/issues/1405)). `scripts/contract/start_gate.py` and `complete_gate.py` must open for run `smoke` in `tests/fixtures/windows_smoke/contract` (freeze evidence, verifier results and the provenance token) and refuse a run with no record.
- `.github/workflows/floor.yml` runs the `floor enforcement` and `floor self-anchor` checks (see [The floor](#the-floor)).
- `.github/workflows/issue-needs-triage.yml` adds the `needs-triage` label to each newly opened issue that does not already carry `agent-ready`, with an `issues: write` token and no checkout ([Definition of ready](./definition-of-ready.md)).
- `.github/workflows/mutation.yml` runs mutation testing weekly (see [Mutation testing](#mutation-testing)).
- `.github/workflows/codeql.yml` (workflow `Security`) runs CodeQL and `pip-audit` (see [Security scanning](#security-scanning)).
- `.github/workflows/doc-sync.yml` (workflow `Doc sync`) runs `/doc-contradictions` on each pull request to `main`, scoped to the doc clusters it touches; not required (see [Doc sync](#doc-sync)).
- `.github/workflows/build-standalone-skills.yml` publishes the standalone skill ZIPs on a version bump (see [Standalone skill pipeline](./standalone-skills.md)).
- `.github/release.yml` configures categorised release notes for `gh release create --generate-notes`. See the file for the label-to-category mapping.

**CI triggers on `main`**: `pull_request` and `push` to `main`, and `merge_group`; `floor.yml`, `pr-lint.yml` and `claude-review.yml` run on a pull request to any base, `codeql.yml` also runs on a weekly `schedule`, and `mutation.yml` runs only on its weekly `schedule` or by hand (`workflow_dispatch`). A PR targeting `main` gets `tests.yml` + `pr-lint.yml` on every synchronize; pushes to other branches with no open PR run neither.

## Lockfiles

`skills/assess/` and `scripts/` each commit a `uv.lock`, and CI installs from them with `uv run --locked`. The `Lockfiles match pyproject.toml` step in `ruff + mypy gates` runs `uv lock --check` in both packages and fails first on a stale lock, so a `pyproject.toml` edit without `uv lock` reads as a lock problem rather than a lint or type failure. A dependency edit commits the re-locked `uv.lock` in the same PR.

## Generated files and goldens

The schemas, the measures catalog, `references/counts-only.md` and the fixture goldens under `skills/assess/tests/fixtures/` are committed generator output. A test byte-compares each against a fresh build, so a stale copy fails CI. `.gitattributes` lists every one as `linguist-generated`, which also folds them out of GitHub diffs. When a PR changes a generator, a renderer or a report, expand the folded files in review: a golden such as the parity report or a team page is where the behaviour change shows.

The four catalog files (`docs/checks.html`, `docs/what-we-measure.md`, `skills/assess/references/measures.json` and `skills/assess/references/counts-only.md`) give each check its own lines, sorted by id or name, and hold no count or total. Two PRs that add different checks therefore change different lines and merge without a conflict; `skills/assess/tests/test_catalog_merge.py` merges two such branches and checks the result equals a fresh build. Two checks whose names sort next to each other can still meet at one spot, as can two additions to a one-element list in `measures.json` (a pair of truth tags that share one condition): take either side and run `make regen`.

The schemas and goldens still conflict on most parallel merges. The recipe for a conflict in any generated file, whichever files it touches:

```bash
git checkout --theirs -- <conflicted generated files>   # or --ours: either side works
make regen
git add -A && git commit
```

`make regen` (in the root `Makefile`) runs every generator in dependency order: the schema modules, `make catalog`, the counts-only document, the fixture builders and the renders built from them, then the goldens their tests rewrite under a `*_REGEN=1` variable. It takes about 30 seconds. It is POSIX-only: on Windows without `make`, run the `regen` recipe lines from the `Makefile` one by one in Git Bash. Never hand-merge a generated file; review the diff `make regen` leaves instead. The fleet golden needs ripgrep (`rg`); without it that step skips and leaves the file as it was.

`tests/test_make_regen.py` (in `plugin contract pytest`) copies the tree, overwrites every `linguist-generated` file with a conflict, runs `make regen` and fails on any remaining diff. A new generated file therefore needs two edits: a `linguist-generated` line in `.gitattributes` and its generator in the `regen` recipe. A few goldens are frozen oracles that no current code may rewrite, so they are left out of both. Under `skills/assess/tests/fixtures/` (relative to the repository root): `structure_golden/` (written by the pre-#708 builder), the captured `/assess` run in `golden/run-context-baseline.json` and `golden/assess-report-baseline.md`, and `fleet_legacy/` (the pre-2.0.0 format). At the root: `tests/canaries/`.

## The type gate

mypy runs `strict` over all of `skills/assess/scripts/` (lib, orchestrators, renderers) with `disallow_any_generics` on for every module and no per-module exception, so a bare `dict` or `list` fails. Known shapes are `TypedDict`s: shared run-context rows and the orchestrators' file shapes, the stats sidecar and `finalize-input.json`, live in `lib/run_context_types.py`; `dict[str, Any]` is for blocks whose keys genuinely vary.

It also covers the `scripts/` build and contract tooling in full, where per-module overrides relax just the flags the floor-protected modules (`floor_anchor.py`, `contract/`, `canaries/`) fail today, and `floor_check.py` stays out. A third run covers `skills/fleet/scripts`, `skills/marathon/scripts`, `skills/refine/scripts` and `skills/doc-contradictions/scripts`, from `skills/assess` with its locked tools and the same strict settings.

A new function needs annotations to pass. Both gates enable `ignore-without-code`, so a bare `# type: ignore` fails; the trailing reason (`# type: ignore[code]  # reason`) is a convention mypy cannot check.

## Markdown contract checks

The `plugin contract pytest` job (`tests/test_plugin_contract.py`) runs these over the shipped markdown:

- `test_internal_links_resolve` over every shipped `SKILL.md`: relative markdown links must point to real files. For an illustrative file mention use inline code (`` `CLAUDE.md` ``), not a clickable relative link.
- `test_no_conflict_markers` over every authored markdown file: an unresolved git conflict (a line-starting `<<<<<<<` / `>>>>>>>` / `|||||||`) fails the build. Markdown has no parser to reject one, which is how `commands/tm.md` shipped for about three weeks with three committed conflict regions (#211/#216). Reference a marker as inline code so it never starts a line.
- `test_no_bare_positional_in_skill_md` over every shipped `SKILL.md`: Claude Code substitutes a skill's arguments into a bare `$0`..`$9` anywhere in the text, fenced or not, which is how the assess skill's `needs_offer` helper ran with argument words as its parameters (#328). The placeholders are 0-based (`$0` is the first argument, per [the skills docs](https://code.claude.com/docs/en/skills.md), "String substitutions"), so shell's `$0` (the script name) is corrupted too. Write shell positionals in brace form (`${0}`, `${1}`); for awk, which has no braced field reference, write the parenthesised `$(1)` or restructure the snippet so it takes no positionals. Named `$name` placeholders are not guarded: they exist only for a skill that declares an `arguments` frontmatter list, and none does; a skill that adds one must avoid bare `$<name>` for each listed name.

## File-size ratchet

`tests/test_file_size_ratchet.py` (in `plugin contract pytest`) holds every Python file under `skills/assess/`, `scripts/`, `skills/fleet/`, `skills/marathon/`, `skills/refine/` and `skills/doc-contradictions/` to the `default_limit` (800 lines) in `.file-size-ratchet.toml`. Files already over it are listed under `[ceilings]` at their line count and may shrink but not grow.

The ceiling follows the file down: a file more than the larger of `shrink_slack_lines` (20) and `shrink_slack_percent` (2) percent of its ceiling below it fails until the ceiling is lowered to the current count, and an entry must be deleted once its file drops to the limit. A file over its limit gets split; raise a ceiling only for justified growth, with a one-line `reason`.

Because a ceiling can move down, two open PRs can each pass alone and fail together: one shrinks an allowlisted file and lowers its ceiling, the other adds lines to the same file. After the first merges, merge `main` into the second and re-run `plugin contract pytest` before merging it.

## Branch protection

`main` has branch protection (`enforce_admins: true`, 0 required approvals). A PR cannot merge unless eight checks are green: `skills/assess pytest`, `scripts/ pytest`, `plugin contract pytest`, `ruff + mypy gates`, `Validate PR title`, `floor enforcement`, `floor self-anchor` and `windows suites + smoke runs`.

Not required: `CodeRabbit`, `Auto-label from PR title`, the conditional `canary suite (semantic layer)`, and the push-only `build` (standalone publish) job. The full non-blocking list, and the `AI-readiness regression gate` that behaves as required, are in [Marathon notes](./marathon.md#ci-patterns).

Verify the live set:

```bash
gh api repos/bjcoombs/ai-native-toolkit/branches/main/protection/required_status_checks | jq .contexts
```

Emergency override: `gh api -X DELETE repos/bjcoombs/ai-native-toolkit/branches/main/protection`, then re-apply.

## The floor

`FLOOR.md` is the constitutional floor of the acceptance-contract workflow: four clauses (cold verification on every run, a contract frozen before decomposition, maintainer sign-off for floor changes, and the immutability of that rule) plus the tokens that mark the files carrying the gate invocations. `.github/workflows/floor.yml` enforces it through the two required floor checks.

A change to the floor core (`FLOOR.md`, `scripts/floor_check.py`, `scripts/floor_anchor.py`, `.github/workflows/floor.yml`, per `FLOOR_CORE_PATHS` in `scripts/floor_check.py`) needs the maintainer's out-of-band approval of the `floor-signoff` environment deployment review, which CI requests automatically. No automated step - retro, marathon teammate, or fix loop - may self-apply that approval or route around it: propose the change and stop.

A change to the gate code (`scripts/contract/`) or the canaries (`scripts/canaries/`, `tests/canaries/`) gets no sign-off request; it must pass `canary suite (semantic layer)` instead. The external-anchor proof is [`floor-anchor-proof.md`](../floor-anchor-proof.md).

## Mutation testing

`.github/workflows/mutation.yml` runs `mutmut` 3.8.0 over a bounded set of `/assess` core modules (`stats_diff.py`, `promissory_markers.py` with its `python_regions.py` helper, `doc_staleness.py`, and the two largest hotspots `doc_graph.py` and `keyhole_signals.py`, about 4.5k mutants as of 2026-10; scope in `[tool.mutmut]` in `skills/assess/pyproject.toml`) weekly and on `workflow_dispatch`, never on PRs. This is Layer 6 truth-pressure: evidence that the tests would fail if the code were wrong, which line coverage cannot show.

It is time-boxed (45m inner timeout, 60m job), prints killed/survived/score per module to the job summary, and uploads `mutmut-results` (the survivor listing plus `mutants/**/*.meta`). Surviving mutants are findings to read, not a red build, so the job is never required. To widen the scope, add a module to `only_mutate` and its test file to `pytest_add_cli_args_test_selection`.

mutmut 3 keys mutants by file path with only a leading `src.` stripped, so the run mutates through `skills/assess/src`, a committed relative symlink to `scripts`. Without it every mutant key misses and mutmut stops before testing any, so the workflow fails loudly when the link is missing or retargeted. `/assess`'s walks (treemap, doc graph, structure graph, test pressure), the file-size ratchet, ruff and mypy do not descend the link, so nothing is counted twice (`skills/assess/tests/test_symlink_walks.py`). After a local run, `rm -rf mutants`; `/assess` skips it anyway.

The `/assess` opt-in mutation pass runs this config as checked out, narrowed to the focus files' mutants, inside its own 300s budget; a group stopped at that budget keeps the verdicts mutmut already saved and is marked `partial`.

## Security scanning

`.github/workflows/codeql.yml` (workflow `Security`) runs CodeQL over Python, JavaScript (`scripts/canaries/*.mjs`) and the workflows themselves, plus `pip-audit` over the Python packages CI and the Assess Gate install (the locked dependency sets of both uv projects, `skills/assess/` and `scripts/`, exported with their dev groups from the committed `uv.lock` files, and every script's PEP 723 inline deps, which commit no lock and resolve fresh), on every PR, push to `main` and weekly. Advisory, and the two parts fail differently:

- A `CodeQL (<lang>)` job goes red only when analysis itself fails. Its alerts land in the Security tab and in a separate `CodeQL` code-scanning check, so a green job does not mean no findings.
- `pip-audit` goes red on a known vulnerability or, under `--strict`, on a resolver error, so read the log before acting.

Fix the code rather than dismissing an alert to clear it.

## Doc sync

`.github/workflows/doc-sync.yml` runs `/doc-contradictions` on each pull request to `main`, over only the documents and code the pull request touched ([#1453](https://github.com/bjcoombs/ai-native-toolkit/issues/1453)). It is not a required check and is not in branch protection.

- **Scope.** `skills/doc-contradictions/scripts/doc_clusters.py --changed-from <base sha>` builds the skill's clusters on the pull request's head and keeps those holding a changed document or a changed subject-code file, plus the cross-cluster pass when a changed file is a hub. `.assess/` is excluded: in the full pass on [#1223](https://github.com/bjcoombs/ai-native-toolkit/issues/1223), 33 of the 54 rejected findings cited that generated run record. With no cluster touched, the model never runs.
- **Model.** A Sonnet orchestrator fans out one `doc-contradictions-comparer` per cluster on Haiku (`CLAUDE_CODE_SUBAGENT_MODEL=haiku`, and `model: haiku` in the agent file). Its tools are subagents and reads of the pull request's files: no Bash, no writes. It runs only for a pull request from a branch of this repository whose author is an owner, member or collaborator. The credential is the secret `REFINE_ANTHROPIC_API_KEY`, then the refiner's Workload Identity Federation variables, then `CLAUDE_CODE_OAUTH_TOKEN`, the refiner's order.
- **Isolation.** The skill, the agent and the scripts are checked out from the pull request's base commit; the head is checked out under `pr-head/` as data, and no script or skill from it runs. The workflow file itself comes from the pull request's merge ref, as for every `pull_request` workflow, so the trusted-author gate is the control on who can change what runs. On the pull request that adds the scripts, the base has none, so the check skips. The `check` job holds `contents: read` and `pull-requests: read` (and `id-token: write` for Workload Identity Federation); only the `post` job, which runs no model, holds `pull-requests: write`.
- **Findings.** `doc_sync_findings.py` checks every citation against the file, as Step 5 of the skill does, and drops the rest. A high-confidence finding with a side in a changed file becomes a review thread on that line (or on the file, when the line is outside the diff), so an open thread holds the merge under the marathon's resolved-threads rule (branch protection does not require conversation resolution) until the document is fixed or the thread is answered. Everything else goes into one `Doc sync` summary comment, edited on each push, which does not block. A run that could not check (over the cluster limit, no credential, model failure) always writes the summary; a clean run or a change touching no cluster writes one only to update an earlier one. Model-written text has `@` mentions neutralised. A thread is posted once per finding across pushes.
- **Off switch.** Set the repository variable `DOC_SYNC_ENABLED` to `false`.

The false-positive rate over its first two weeks is recorded on #1453 before anyone decides whether to make it required.

## Coverage floor

There is no coverage target, only a floor that stops coverage falling. The `skills/assess pytest` and `scripts/ pytest` jobs print a term summary and upload a Cobertura `coverage.xml` artifact each (`coverage-skills-assess`, `coverage-scripts`), and fail when line coverage drops below `[tool.coverage.report] fail_under` in that package's `pyproject.toml`: 93 for `skills/assess` (measured 93.44%), 91 for `scripts/` (measured 92.14%).

The floor lives in config rather than as `--cov-fail-under`, so a local pytest-cov run from inside that package directory enforces it too; the repo-root recipe below enforces only the `scripts/` floor, because coverage.py reads `pyproject.toml` from the current directory. It is a ratchet: raise it when coverage rises, and never lower it without a stated reason in the PR that does. Filenames in those artifacts are relative to the job's package directory, not the repo root.

Test coverage focuses on the deterministic core under `skills/assess/`. `complexity-treemap.py` is smoke-tested rather than unit-tested: it is a thin CLI wrapper around lizard/squarify.

### Coverage for `/assess`

`/assess` never runs the suites. It reads an existing `coverage.xml` or `lcov.info` from the repo root (or `coverage/`, `.coverage/`) to fill its "Where to focus testing" table. To give it one, run this from the repo root before `/assess`; it writes a gitignored `coverage.xml` with repo-relative filenames covering both packages. The `scripts/` suite must run from inside `scripts/` (some tests read `../skills/...`), hence the subshell and the combine step:

```bash
GIT_CONFIG_GLOBAL=/dev/null uv run --project skills/assess --with pytest --with pytest-cov --with pyyaml pytest skills/assess -q --cov=skills/assess/scripts --cov-report= \
  && (cd scripts && uv run --with pytest --with pytest-cov pytest -q --cov=. --cov-report=) \
  && uv run --with coverage coverage combine --keep --data-file=.coverage.all .coverage scripts/.coverage \
  && uv run --with coverage coverage xml --data-file=.coverage.all -o coverage.xml
```

## Local runs and git config

`skills/assess/tests/conftest.py` points `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` at the null device at import time, so ambient commit signing or hooks cannot fail the git-backed tests in that suite. Nothing does the same for `scripts/tests/` (`test_floor_check.py` runs `git commit` in temp repos), and scripts run outside pytest (for example `assess_core.py`) still read global config; prefix those with `GIT_CONFIG_GLOBAL=/dev/null` if it signs commits or runs hooks.
